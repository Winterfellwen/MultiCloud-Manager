# CloudOps AI 全方位审计报告

> **审计日期：** 2026-07-17
> **审计范围：** 6 维度 × 15 模块横向评审
> **对标平台：** AWS Console, Azure Portal, GCP Console
> **审计方法：** 功能遍历 → 截图取证 → 对标分析 → 差距评级 → 报告输出

## 维度四：监控告警 (2/5)

### 指标可视化

- **仅采集 `cpu_usage_percent`** — 未采集 memory/network/disk I/O
- 前端用 recharts 面积/线形图，仅实例级别
- 无可跨实例聚合图表
- 无指标浏览器/即席查询

### 告警规则

- 条件字符串正则解析 (`> 85`)，支持 `>=/<=/>/</==`
- 无复合条件 (CPU > 80% AND Memory > 90%)
- 无动态阈值（静态阈值 vs Azure ML 动态阈值）
- 无静默时间/维护窗口
- 无告警关联/分组
- 条件评估用 `some()`（任意单点触发）而非聚合

### 通知渠道

- 3 种渠道: webhook / email (nodemailer) / slack
- 无 Teams/Discord/PagerDuty/OPSgenie/SMS/电话
- webhook secret 存储但未用于 HMAC 验证
- 无通知频率限制/节流

## 维度六：AI Agent (4/5)

### 工具架构

- 三层架构: Registry → Planner → Executor
- 15 个工具，4 个类别（Cloud Instances / Cloud Resources / Monitoring / System）
- 结构化的 JSON Schema 参数定义
- 可用性检查（环境变量检测）

### 多步推理

- Agent Loop: 调用 LLM → 解析 tool_calls → 并行执行 → 结果回传
- 上下文窗口管理: 最多 40 条消息，孤儿工具消息修剪
- `maxIterations` 终止 + `MAX_STEPS_PROMPT` 强制最终回答
- 断线恢复: In-flight run 快照

### 安全模型

- **Plan** 模式: 仅安全工具，危险操作自动拒绝
- **Action** 模式: 自动批准所有操作
- **Confirm** 模式: 危险操作需人工审批对话框(60s 超时)
- Approve/Reject 通过 WebSocket 事件广播

### 工具目录

- 搜索 + 风险等级过滤 + 提供商过滤
- 卡片网格: 工具标签、描述、风险等级、提供商 tags
- 执行历史可展开

### 优势

- 流式输出 + 工具调用卡实时展示
- WebSocket + ACP 事件账本保障断线恢复
- 完整的工具审计（args/result/duration/user/session）
- 三模式安全设计合理

### 差距

- 审批状态仅内存存储 — 进程重启丢失待审批项
- 无"在聊天中测试"按钮
- `shell_execute` 工具可执行任意命令，缺少 allowlist/denylist

## 维度七：架构质量 (3/5)

### 代码组织

- 清晰的 monorepo 结构: cloud-service / auth-service / ai-agent / ai-gateway / web-console / shared
- 插件式提供商架构: `ICloudProvider` 接口

- 仅 ai-gateway 有单元测试
- 无 cloud-service 提供商测试
- 无集成测试/负载测试/安全测试
- 21 个 `test_*.py` 调试脚本散落在根目录

## 总结

CloudOps AI 拥有 **扎实的 AI Agent 架构**（15 工具的 Registry/Planner/Executor 体系、Plan/Action/Confirm 三模式安全、完整的工具审计）和 **拓扑视图等亮点 UI**，但在基础功能完整性上存在多个 P0 断裂点。

主要瓶颈在于：
1. **核心路径断裂** — 资源详情页和审计日志页均报错，用户核心任务受阻
2. **全局搜索缺失** — 对标三大云平台的导航基石功能
3. **成本管理基本空白** — 无图表、无预算、无预测
4. **测试覆盖极低** — <10%，影响迭代信心

产品阶段判断：**早期 Beta 阶段**。AI Agent 能力已达到可发布水平，但基础云管理功能需要大量打磨才能进入 GA。
